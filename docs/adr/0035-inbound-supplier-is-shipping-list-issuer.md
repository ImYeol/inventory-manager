# ADR-035: 입고처는 출고 리스트 파일을 발행하는 주체이며 파싱 템플릿을 소유한다

**결정**: 소싱의 중심 엔티티를 "출고 리스트 파일을 발행하는 주체"로 고정하고 UI 용어를 `입고처`로 통일한다. 입고처는 공장 자신일 수도, 1688 등 구매를 대행하는 배대지(포워더)일 수도 있지만 둘을 구분하는 타입/판별 필드는 두지 않는다 — 어느 쪽이든 "이 파일을 보낸 곳"이라는 동일한 역할만 필요하기 때문이다. 기존 `Factory`/`factories` 테이블을 그대로 재사용하며(이미 입고 파이프라인 전체가 이를 공급자로 사용 중이다), 테이블·컬럼·함수명(`supplier_id`, `Factory`, `factories`)은 바꾸지 않는다. 이 문서와 `CONTEXT.md`가 소유하는 것은 UI 라벨과 문서 용어(`입고처`)뿐이다.

`inbound_templates.supplier_id`를 NOT NULL로 두고 입고처와 파싱 템플릿을 N:1로 묶는다(한 입고처가 여러 템플릿을 가질 수 있다). 엑셀 양식이 바뀌면 새 템플릿을 만드는 대신 기존 `inbound_template_versions`의 새 불변 버전으로 흡수한다 — "기본 템플릿" 플래그 같은 추가 상태는 만들지 않는다. 입고 등록 흐름은 `입고처 -> 템플릿 -> 파일` 순서를 강제한다: 템플릿 select는 항상 렌더되지만 선택된 입고처의 템플릿으로만 채워지고, 활성 템플릿이 정확히 하나면 자동 선택된다. 입고처를 고르기 전에는 템플릿 select와 "템플릿 만들기" 버튼을 비활성화한다. 인라인 템플릿 생성(`ParseTemplateBuilder` 재사용)은 그대로 두되, 저장 시 별도 소유자 선택 없이 현재 선택된 입고처가 자동으로 소유자가 된다.

설정의 `파싱 템플릿 관리`(`/settings/parse-templates`)는 해체한다. 입고 템플릿의 목록·생성·버전 이력은 `소싱 > 입고처`의 입고처 상세 modal로 옮긴다 — 템플릿이 입고처에 종속된 지금은 "설정이 cross-cutting 설정을 소유한다"는 ADR-034의 근거가 더 이상 성립하지 않고, 오히려 소유 엔티티(입고처) 옆에서 관리하는 편이 자연스럽다. 주문 송장 파싱 프리셋은 이미 주문 송장 등록 modal 안에서 관리되므로 옮길 대상이 없다. `/settings/parse-templates`는 ui-guide.md 17번 규칙에 따라 얕은 redirect alias만 남긴다. `소싱 > 외부 공장` 메뉴 라벨은 `소싱 > 입고처`로 바꾸되 라우트(`/sourcing/factories`)는 유지한다.

**구매 플랫폼(1688 등) 태그는 이번 범위에서 구현하지 않는다.** 필요해지면 이미 존재하는 템플릿 매핑의 임의 추가 컬럼 슬롯(`mappings.source: Record<string,string>`, 행 단위로 `inbound_import_source_rows.source_values`에 저장됨)에 구매 플랫폼 값을 하나의 소스 컬럼으로 캡처하면 된다. 이는 스키마 변경 없이 확장 가능하다.

**이유**: 어떤 소싱 채널이든 운영자가 실제로 상호작용하는 대상은 "출고 리스트 파일을 보낸 곳" 하나뿐이다. 공장/배대지 구분을 스키마에 넣으면 향후 실제로 필요해질 수도 있는 속성(구매 플랫폼, 대행 수수료 등)과 뒤섞여 엔티티 경계가 흐려진다. 파싱 템플릿을 입고처에 N:1로 묶는 이유는 같은 입고처가 보내는 파일 양식은 실무적으로 반복되기 때문이며, 등록 순서를 강제하는 이유는 템플릿이 입고처 없이는 의미가 없어졌기 때문이다(비어 있는 전역 템플릿 목록에서 고르게 하면 잘못된 입고처의 템플릿을 실수로 재사용할 위험이 생긴다).

**트레이드오프**: 입고처 상세 modal이 이제 연락처 정보와 파싱 템플릿 관리라는 두 책임을 함께 갖는다. `/settings/parse-templates`를 완전히 지우지 않고 redirect alias로 남기는 이유는 기존 북마크·문서 링크가 깨지지 않게 하기 위해서이며, 이는 alias 유지 비용을 남긴다. 구매 플랫폼 태그를 미루는 대신 `mappings.source`라는 범용 슬롯에 의존하므로, 실제로 태그가 필요해지면 그 값이 임의 텍스트 컬럼일 뿐 정규화된 필터 가능 속성은 아니라는 한계가 있다.
