# PRD: Console IA Consolidation And Table-First Reset

## 한 줄 목표
Seleccase Inventory를 `dashboard 내부 분석 + 주문·송장 작업 + 상품 관리 table-first + 테이블 중심 재고 운영 + 설정 내부 스토어 연결 + sourcing table/modal` 흐름으로 재정리한다.

## 현재 문제
- `상품 관리`와 `기준 데이터`라는 표현이 섞여 있어 상품/창고 기준정보의 주인이 무엇인지 한눈에 읽히지 않는다.
- `src/app/components/inventory/InventoryWorkspace.tsx`의 개요 화면은 창고 선택 외에 실질적인 컬럼 필터, 검색, 컬럼 가시성 제어가 부족해 재고 표를 작업 표면으로 쓰기 어렵다.
- `src/app/(protected)/inout/InOutForm.tsx`는 입고/출고 버튼으로 진입한 뒤에도 다시 입고/출고를 고르게 하고, `표 붙여넣기` 패널까지 포함해 팝업의 섹션 수가 과도하다.
- 재고 운영 화면은 헤더, 탭, CTA, 보조 배지, 탭 내부 설명이 동시에 쌓여 실제 표보다 chrome이 먼저 보인다.
- `src/app/(protected)/shipping/ShippingView.tsx`는 업로드 화면 안에 `연동 준비 상태`, 채널별 미연결 카드, 이동 버튼을 반복해 같은 맥락을 여러 번 설명한다.
- 운송장 업로드 뒤에는 원본 엑셀 행만 보여주고 있어, 사용자가 어떤 행이 네이버/쿠팡으로 분류됐는지 즉시 파악하기 어렵다.
- `src/app/(protected)/integrations/IntegrationsView.tsx`와 `src/app/(protected)/settings/SettingsView.tsx`가 스토어 연결 책임을 나눠 갖고 있어 설정 구조가 겹친다.
- 대시보드와 분석이 같은 지표를 다른 메뉴에서 반복해 보여 주고 있어 그래프와 이동 비용이 중복된다.
- 재고 운영, 상품 관리, 운송장, 소싱 모달에 legacy native `<select>` 스타일이 섞여 있어 dropdown 상호작용과 시각 언어가 일관되지 않다.
- 상단 제목/서브타이틀, 설명 카드, 안내용 섹션이 실제 작업 표면보다 커서 AI slop처럼 느껴지는 빈 여백과 중복 copy가 생긴다.
- `기준 데이터`와 `/integrations`는 더 이상 canonical source of truth가 아니어야 하는데, 현재 문서와 화면 곳곳에서 아직 주인처럼 보인다.

## 사용자
- 상품/창고 관리자: 상품과 창고 기준정보를 빠르게 찾고, 이름과 상태를 직접 수정해야 한다.
- 창고 관리자: 창고별 재고를 표에서 바로 보고 상품명, 창고, 상태 기준으로 빠르게 걸러야 한다.
- 운영 매니저: 입고/출고를 최소 입력으로 다건 처리하고, 복잡한 보조 섹션 없이 결과만 빨리 확인하고 싶다.
- 배송 담당자: 엑셀 업로드 직후 어떤 행이 네이버/쿠팡 주문과 매칭됐는지 배지와 필터로 확인하고 싶다.
- 관리자: 설정 화면 안에서 네이버/쿠팡 연결 상태를 보고 연결/변경을 처리하고 싶다.

## 핵심 재설계 판단
- `상품 관리`는 상품/창고 기준정보의 top-level domain이다.
- `재고 운영`은 목록과 이력 view, 입고/출고 action 중심의 운영 허브다.
- `설정`은 `스토어 연결`의 canonical owner다.
- `운송장`은 연결 설명 페이지가 아니라 `업로드 → 미리보기 → 분류 → 매칭/발송` 실행 화면이다.
- `기준 데이터`는 top-level destination이 아니라 `상품 관리`의 과거 표현으로만 남는다.
- `/integrations`는 별도 owner가 아니라 `설정 > 스토어 연결`로 보내는 legacy alias다.
- 중복 설명 카드와 장식용 안내 섹션은 제거하고, 실제 작업 표면을 먼저 보여준다.

## 목표 정보 구조
```text
대시보드
└── 분석 섹션
상품 관리
├── 상품
└── 창고
재고 운영
소싱
├── 입고처
└── 입고 예정
주문
└── 송장 업로드/반영
계정 메뉴
└── API 설정 → 설정 (/settings?section=store-connections)
```

승인된 primary navigation 순서는 `대시보드 / 주문 / 상품 관리 / 재고 운영 / 소싱`이다. API 설정은 하단 계정 메뉴의 `/settings?section=store-connections` deep link로 제공하며, `/settings`는 송장·연결 흐름의 deep link owner와 연결 편집의 canonical owner로 유지한다. `/orders`가 주문 조회, 주문 예약, 송장 업로드/반영의 canonical owner이며, 기존 `/shipping`은 `/orders/tracking-import`로 redirect하는 호환 경로다.

## 메뉴 원칙
- 1차 메뉴는 직접 가치가 있는 목적지여야 한다.
- 확장형 메뉴는 2개 이상 의미 있는 child screen이 있을 때만 사용한다.
- `대시보드`는 KPI와 분석 차트를 함께 가진다.
- `상품 관리`는 top-level direct item으로 두고, 내부에서 `상품`과 `창고`를 구분한다.
- `소싱`은 확장형을 유지한다.
- `주문`, `재고 운영`은 direct item으로 유지한다.
- `API 설정`은 계정 메뉴에서 제공하고, `스토어 연결`은 `/settings`의 canonical section으로 둔다.

## UI Complexity Budget
- 새 기능은 새 카드나 새 설명 섹션을 늘리기 전에 기존 toolbar, table, header, action rail 안에서 해결하는 것을 우선한다.
- 각 운영 화면은 실제 작업 surface가 제목/설명/chrome보다 먼저 보여야 한다.
- 전역 액션은 가능한 한 compact group으로 묶고, 같은 상태를 카드/배지/문장/버튼으로 반복하지 않는다.
- 버튼 라벨은 짧은 동사를 기본으로 하고, provider명과 상태명을 한 줄에서 반복하지 않는다.

## 핵심 시나리오
1. 사용자는 `상품 관리`로 이동해 상품과 창고 기준정보를 수정한다.
2. 사용자는 `대시보드`에서 KPI와 분석 차트를 함께 보고, 차트별로 모델/기간/날짜를 독립적으로 조정한다.
3. 사용자는 `재고 운영`으로 이동한다.
4. 상단 툴바에서 창고, 상품명, 상태, 옵션, 컬럼 표시를 조정하며 재고 표를 바로 필터링한다.
5. `입고` 또는 `출고`를 누르면 고정 타입의 빠른 입력 팝업이 열리고, 최소 필드만 포함된 편집 테이블에서 다건 입력한다.
6. 복잡도가 높아지면 `CSV`와 `이력`은 `재고 운영` 하위 페이지에서 별도로 다룬다.
7. 사용자는 `설정`에서 네이버/쿠팡 연결 상태를 보고 연결하거나 값을 변경한다.
8. 사용자는 `주문`에서 송장 엑셀을 업로드한다.
9. 시스템은 연결된 스토어에서 주문을 조회하고 이름/주소를 비교해 업로드 행을 `네이버`, `쿠팡`, `미분류`, 필요 시 `중복 후보`로 분류한다.
10. 사용자는 분류 배지와 필터를 이용해 미분류 행만 확인하거나 채널별로 발송 대상을 정리한다.
11. 사용자는 `소싱 > 입고처`에서 입고처 목록을 표로 보고, 행 상세 modal과 등록 modal로 작업한다.

## 기능 요구사항

### 0. 대시보드 + 분석 통합
- `분석`은 독립 1차 메뉴가 아니라 `대시보드` 내부 섹션이다.
- 대시보드는 빠른 이동 버튼 대신 `KPI + 3개 분석 차트 + 운영 표면`으로 구성한다.
- 유지 차트는 `거래 추이`, `재고 추이`, `창고별 변동 비교` 3개다.
- 각 차트는 자기 전용 control strip를 가진다.
  - 모델 선택
  - 시작일
  - 종료일
  - 필요 시 집계 단위
- `ModelPieChart`와 모델 요약 표는 제거한다.
- `/analytics`는 legacy 접근만 보존하는 redirect route로 남긴다.

### 1. 상품 관리
- `상품 관리`는 상품과 창고 기준정보의 top-level owner다.
- 이 화면은 다음 두 책임을 분리해 제공한다.
  - `상품`: SKU, 옵션, 상태, 상품명 등 실제 재고 운영에서 참조되는 상품 속성
  - `창고`: 창고명, 사용 여부, 식별 정보, 운영 메모 등 재고가 머무는 장소 속성
- `상품 관리`는 `재고 운영`의 조회 대상 데이터를 제공하지만, 재고 수량 자체를 소유하지는 않는다.
- 내부 `ProductVariant`의 seller SKU와 실제 창고 수량이 source of truth다. 채널 상품 등록·수정·전량 수집은 Seleccase 범위 밖이며, 상품 탭의 canonical owner는 내부 SKU 목록이다.
- `ChannelProductRef`는 사용자가 입력한 채널 판매 옵션 식별자와 내부 SKU의 명시적 매핑이다. 내부 SKU 하나는 채널별 옵션을 여러 개 가질 수 있다. 매핑 입력은 판매자 SKU, 채널 상품 ID, 채널 옵션 ID를 받고 server action에서 존재를 검증한다. 상품명 유사도나 SKU 자동 연결을 하지 않는다.
- `내부 상품 등록`은 채널에 없는 로컬 상품을 만드는 보조 modal이다. 상품명과 SKU prefix는 필수이고 사이즈·색상은 선택값이다. 옵션이 없으면 단일 판매 옵션과 prefix 자체를 판매자 SKU로 만든다.
- `기준 데이터`는 내부 설명이 아니라 `상품 관리`를 가리키는 과거 표현으로만 취급한다.
- `상품` 탭은 `검색 + 고정 보기 + 내부 상품 등록`이 가능한 SKU 중심 table workspace다. 전량 채널 상품 수집은 canonical flow가 아니다.
- 채널에 없는 상품만 `내부 상품 등록` modal에서 생성한다. 사이즈·색상은 실제 판매 옵션이 있을 때만 입력한다.
- `창고` 탭도 같은 toolbar + table 패턴을 사용한다.

### 2. 재고 운영 허브
- `재고 운영`은 단일 first-level hub로 유지한다.
- 기본 워크스페이스는 다음을 가진다.
  - `목록`
  - `이력`
  - `입고`
  - `출고`
  - `CSV`
- `이력`은 이미 top-level `/history` standalone route로 제공되며, `CSV`가 한 화면 UX를 과도하게 복잡하게 만들면 `/inventory/csv` 하위 페이지로 추가 분리할 수 있다.
- 창고 컨텍스트는 허브 공통 상태로 유지한다.

### 3. 재고 목록 테이블
- 목록의 기본 레이아웃은 `compact filter bar + dense table`이어야 한다.
- 표는 최소 다음 정보를 제공한다.
  - 상품명
  - 옵션
  - 창고
  - 현재 재고
  - 최근 입고
  - 최근 출고
  - 상태 배지
- 최소 다음 필터를 지원한다.
  - 창고 dropdown
  - 상품명 검색
  - 상태 필터
  - 필요 시 옵션/재고 상태 보조 필터
- 컬럼 표시/숨김 dropdown을 지원한다.
- 행 애니메이션은 표 가독성을 해치지 않는 미세한 수준으로 제한한다.
- 선택형 필터는 native `<select>`를 새로 쓰지 않고 shared select primitive로 통일한다.

### 4. 빠른 입고/출고
- 상단 `입고` 버튼은 입고 전용 팝업만 연다.
- 상단 `출고` 버튼은 출고 전용 팝업만 연다.
- `재고 추가`는 별도 action으로 제공하지 않는다. 입고는 아직 재고 행이 없는 상품 옵션+창고 조합에는 첫 입고 원장을 만들고, 기존 조합에는 현재 수량을 증가시키는 유일한 수동 입고 action이다.
- 출고는 현재 `onHand`를 줄이는 수동 조정 action이다. 주문 발송으로 인한 출고는 주문 처리 흐름에서 자동으로 처리하며 빠른 출고와 혼동하지 않는다.
- 팝업 안에 다시 `입고/출고` 전환 버튼을 두지 않는다.
- 팝업은 최소 섹션만 가진다.
  - 제목
  - 공통 컨텍스트(창고, 날짜)
  - 편집 테이블
  - 검증/저장 footer
- 기본 입력 방식은 compact editable table이다.
- 편집 표의 사용자 용어는 `상품`, `사이즈`, `색상`, `수량`을 사용한다. 내부 legacy `models` 테이블명은 노출하지 않는다.
- 유지할 기능:
  - 행 추가
  - 행 삭제
  - 마지막 행 복제
  - inline validation
- 제거할 기능:
  - `표 붙여넣기`
  - 팝업 안의 중복 타입 전환
  - 설명만 하는 보조 카드

### 5. CSV와 이력의 분리 기준
- `CSV`와 `이력`은 기본적으로 허브 내부에서 시작한다.
- 다음 중 하나가 발생하면 재고 운영 하위 페이지로 분리한다.
  - 툴바와 표가 동시에 과밀해져 같은 CTA가 반복된다.
  - 감사성 메타데이터 때문에 목록/이력 표 가독성이 무너진다.
  - 모바일에서 한 화면에 유지하기 어렵다.

### 6. 설정 안의 스토어 연결
- `설정` 화면은 `스토어 연결`의 canonical owner가 된다.
- 네이버/쿠팡 각각에 대해 다음을 표시한다.
  - 연결 여부
  - 마스킹된 요약
  - 최근 변경 시각
  - `연결` 또는 `변경` 버튼
- 쿠팡 연결 정보에는 `기본 택배사 코드`를 포함한다.
- provider별 상태 요약과 편집 form은 가능한 한 같은 surface 안에 둔다.
- provider별 deep link 또는 section focus를 지원한다.
- `/integrations`는 새 owner가 아니라 `설정 > 스토어 연결`로 보내는 alias/redirect 후보로 간주한다.
- 상태 표현은 `초록/빨강 원형 dot + label` 조합으로 통일한다.

### 7. 주문과 송장 업로드
- `/orders`는 주문 조회, 주문 예약, 송장 업로드/반영을 소유한다. `/shipping`은 독립 작업 surface가 아니라 `/orders/tracking-import` redirect다.
- `운송장` 화면에서 `연동 준비 상태` 같은 별도 설명 섹션은 제거한다.
- 업로드 섹션 아래의 첫 번째 표는 원본 엑셀 행이 아니라 `분류된 업로드 미리보기`가 되어야 한다.
- 네이버가 연결되어 있으면 네이버 주문을 조회해 이름/주소 비교로 해당 row를 분류한다.
- 쿠팡이 연결되어 있으면 `발주서 목록 조회 v5`로 주문을 조회하고 이름/주소 비교로 해당 row를 분류한다.
- 쿠팡 조회는 업로드 엑셀의 날짜 컬럼 범위를 우선 사용하고, 필요 시 `nextToken`으로 다음 페이지를 계속 조회한다.
- 분류 결과는 badge로 표시한다.
  - `네이버`
  - `쿠팡`
  - `미분류`
  - 필요 시 `중복 후보`
- 사용자는 최소 다음 필터를 사용할 수 있어야 한다.
  - 전체
  - 네이버
  - 쿠팡
  - 미분류
- 연결되지 않은 provider는 비활성 상태 설명 대신 활성 버튼으로 노출하고, 클릭 시 해당 provider 설정 section으로 이동시킨다.
- 운송장 헤더는 `네이버 연결`, `쿠팡 연결` 버튼과 compact 상태 rail만 남긴다.

### 8. 송장 핵심 흐름 유지
- 기존 `업로드 → 미리보기 → 매칭/발송` 흐름은 유지한다.
- 분류 표는 발송 대상 정리에 필요한 1차 surface가 된다.
- 채널별 발송 액션은 분류 결과를 기반으로 계산한다.
- 채널별 발송 액션은 분류 표의 preview toolbar action rail에 붙이는 편을 우선한다.
- 운송장 provider action은 `상태 chip + 갱신 + 반영`의 compact group으로 통일한다.
- 쿠팡 송장 업로드는 `shipmentBoxId + orderId + vendorItemId` 기준 item payload로 전송한다.
- 쿠팡 송장 업로드는 설정의 `기본 택배사 코드`를 사용하고, v1 범위에서는 일반배송만 지원한다.
- 운송장 번호가 없는 행도 분류 미리보기에는 남기되, 채널 반영 대상에서는 제외한다.

### 9. 채널 상품과 재고 상태 모델
- `ProductVariant`는 실제 판매·재고 단위이며, 옵션 조합마다 하나의 재고 상태를 가진다.
- 내부 `ProductVariant`의 seller SKU와 실제 창고 수량이 source of truth다. `ChannelProductRef`는 사용자가 입력한 채널 판매 옵션 식별자와 `ProductVariant`를 연결하는 명시적 매핑이며, 하나의 내부 SKU는 채널별 옵션을 여러 개 가질 수 있다. 매핑 입력은 판매자 SKU, 채널 상품 ID, 채널 옵션 ID를 받고 server action에서 존재를 검증하며, 상품명 유사도나 SKU 자동 연결을 하지 않는다.
- 재고 상태는 다음 값을 분리한다.
  - `onHand`: 실제 보유 수량
  - `committed`: 접수된 주문으로 예약된 수량
  - `available`: 판매 가능한 수량(`onHand - committed`)
  - `incoming`: 공장 공급 참고 수량이다. 검수 전에는 available 및 채널 재고에 포함하지 않는다.
  - `channelReported`: 가장 최근 채널에 절대 수량으로 보고한 값
- 주문이 확정되면 `committed`를 증가시켜 예약하고, 현재 `available` 절대 수량을 두 채널의 모든 매핑 옵션에 반영한다. 외부 발송 성공 후에만 같은 트랜잭션에서 `onHand`를 차감하고 예약을 해제한다. 취소는 예약만 해제하며, 반품은 검수 입고 뒤에만 `onHand`를 복구한다.
- 채널 동기화는 증감값이 아닌 현재 `available`의 절대 수량을 전송한다. 동기화 실패는 내부 원장을 되돌리지 않고 최신 absolute quantity를 재시도·재조정하며, 성공 응답 뒤에만 `channelReported`를 그 절대 수량으로 갱신한다.

### 9. 소싱 > 입고처 / 입고 예정
- 공급자 엑셀, 외부 SKU 연결, 창고 분할, 부분·초과·부족·후속·정정의 전체 acceptance contract는 [Inbound receiving](./inbound-receiving.md)을 따른다.
- `입고처`는 카드형 목록이 아니라 `검색 + 상태 필터 + 등록 버튼 + table` 구조를 쓴다.
- 공장 등록은 modal로 처리한다.
- 공장 상세는 행 클릭 또는 상세 버튼으로 여는 modal에서 확인한다.
- 공장 상세 modal에서 활성/비활성 토글을 수행한다.
- `입고 예정`의 공장/모델/사이즈/색상/창고 선택도 shared select primitive를 사용한다.
- `/sourcing/arrivals`는 공급자 엑셀 흐름의 단일 UI owner다. 재고 운영에서 같은 import sheet를 중복 노출하지 않는다.

## 비기능 요구사항
- 기존 `inventory`와 `transactions` 원장 구조는 유지한다.
- 기존 사용자 스코프와 RLS 가정은 유지한다.
- 표와 필터는 desktop 우선 dense layout을 쓰되, 모바일에서는 우선순위 컬럼만 남기거나 stacked layout으로 축소한다.
- body text는 14px 이상, 탭/버튼/입력은 44px 이상을 유지한다.
- 상단 타이틀과 설명은 최소화하고, 같은 맥락을 카드/배지/문장으로 반복하지 않는다.
- 선택형 dropdown은 shared primitive 하나로 통일하고 legacy native `<select>`는 남기지 않는다.
- 새 UI 요구사항은 먼저 action consolidation과 component budget 관점에서 검토한다.
- 설계/구현/리뷰 단계에서 `toolbar-first`, `primary surface first`, `minimal components` 원칙을 공통 기준으로 사용한다.

## MVP 제외 사항
- 범용 커넥터 프레임워크
- 바코드/스캐너 연동
- 자동 재주문/추천 엔진
- 창고 간 이동 자동화
- 승인 워크플로우

## 성공 기준
- `상품 관리`가 top-level domain으로 보이고, 상품과 창고 책임이 분리되어 있다.
- `대시보드`에서 KPI와 분석 차트를 같은 화면에서 보고, 차트별 조건을 독립적으로 조정할 수 있다.
- 재고 표에서 창고와 상품명 기준 필터링이 한 화면 안에서 즉시 가능하다.
- 입고/출고 팝업은 고정 타입이며, 표 붙여넣기 없이도 다건 입력이 빠르다.
- `스토어 연결` 편집 위치가 `설정`으로 단일화된다.
- 운송장 업로드 직후 각 row의 채널 분류가 배지로 보이고, 미분류만 따로 볼 수 있다.
- 소싱 공장 목록이 table + modal 흐름으로 바뀌어 카드 탐색 없이 작업할 수 있다.
- 불필요한 타이틀/서브타이틀/설명 카드가 제거되어 실제 표와 액션이 먼저 보인다.
